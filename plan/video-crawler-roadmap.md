# 视频爬虫未实现功能与未来路线

> 记录日期：2026-06-25  
> 范围：根据最近两次关于“哪些网站能爬/不能爬”和“选 2：根据计划完善代码”的讨论整理。当前阶段只记录计划，不实施代码修改。

## 当前能力边界

当前视频爬虫是通用 MP4 / M3U8 嗅探下载器，而不是大型平台专用解析器。它的优势是处理裸露直链、普通 HLS 和网页里能被浏览器直接请求到的媒体流；弱点是缺少大平台协议适配、完整会话继承、DASH/MPD、DRM 识别提示和复杂 HLS 边界。

## 当前相对可行的网站类型

1. 直接 MP4 地址

   无登录、无复杂鉴权、服务器允许普通 HTTP 请求访问时最稳。

2. 直接 M3U8 / HLS 地址

   标准 TS 切片、fMP4 `EXT-X-MAP`、基础 AES 加密流相对适合当前实现。

3. 普通网页中裸露的 MP4 / M3U8

   页面用浏览器打开后，如果真实媒体流出现在网络请求里，当前 Playwright 嗅探机制有机会抓到。

4. 小型站点或自建站

   尤其是未使用强登录态、DRM、DASH 或复杂请求签名的网站。

## 当前大概率不可行或不稳定的网站类型

1. 大型平台播放页

   如 YouTube、B 站、抖音、快手等。当前没有专用站点解析器，也没有处理平台签名、分离音视频流、风控参数、登录态和动态接口。

2. DASH / MPD 流

   当前只识别 MP4 和 M3U8，不支持 `.mpd`、DASH 分离音视频、分段索引和音视频合并。

3. DRM 保护内容

   如 Widevine、FairPlay、PlayReady、EME 加密播放。后续可以做“识别并提示不支持”，但不建议也不应该做 DRM 绕过。

4. 强登录、验证码、年龄验证、地区限制网站

   当前嗅探阶段可能能看到流地址，但下载阶段没有完整继承浏览器 Cookie、LocalStorage 和临时授权头，容易出现 403。

5. 请求头校验严格的网站

   如果切片请求依赖特定 Cookie、Referer、Origin、Range、Token 或动态 Header，当前实现可能失败。

6. 复杂 HLS

   多 Key 轮换、每切片 IV、`EXT-X-BYTERANGE`、多 `EXT-X-MAP`、`EXT-X-DISCONTINUITY`、多音轨/字幕、直播滚动 playlist 都还没有完整支持。

## 尚未实现但建议优先补齐的功能

### 1. 诊断模式

目标：用户输入 URL 后，不一定立刻下载，而是先告诉用户当前工具看到了什么、为什么不能下载。

建议识别：

- 是否发现 MP4；
- 是否发现 M3U8；
- 是否发现 MPD / DASH；
- 是否疑似 DRM；
- 是否可能需要 Cookie / 登录态；
- 是否因 403、404、超时、M3U8 解析失败或 FFmpeg 合并失败而不能继续；
- 捕获到多少候选流，最终选择哪一个。

收益：用户能区分“软件出错”和“这个网站当前不在能力范围内”。

### 2. 浏览器会话继承

目标：解决“浏览器能播放，但下载器拿到真实流后 403”的常见问题。

建议继承：

- Cookie；
- Referer；
- Origin；
- User-Agent；
- Authorization；
- Accept / Accept-Language；
- 后续可扩展到站点必要的自定义头。

注意：诊断结果和日志中不要明文展示 Cookie、Authorization、Token 等敏感信息。

### 3. HLS 边界补强

当前已支持传统 TS、fMP4 `EXT-X-MAP`、基础 AES 和少量切片失败容忍，但仍缺少：

- 多 Key 轮换；
- 每切片 IV；
- HLS 默认 IV 规则；
- `EXT-X-BYTERANGE`；
- 多 `EXT-X-MAP`；
- `EXT-X-DISCONTINUITY`；
- 多音轨 / 字幕；
- 直播流和滚动 playlist。

建议优先级：多 Key/IV → BYTERANGE → DISCONTINUITY → 多音轨/字幕 → 直播。

### 4. DASH / MPD 支持

很多现代平台使用 DASH，而不是 HLS。需要新增：

- MPD 解析；
- 视频轨和音频轨分别下载；
- 画质选择；
- 音视频 mux 合并；
- 断点续传；
- 清晰提示“不支持 DRM”。

建议将 DASH 做成独立适配器，不要塞进现有 HLS 下载函数。

### 5. 站点适配器架构

当前 `UniversalVideoSpider` 同时负责 URL 判断、网页嗅探、下载、合并和 UI 回报，后续会越来越重。建议逐步拆成：

- `DirectMp4Adapter`；
- `HlsAdapter`；
- `PageSnifferAdapter`；
- `DashAdapter`；
- 特定站点 Adapter。

适配器选择顺序建议为：直接 URL → 已知站点适配器 → 通用网页嗅探 → 诊断失败报告。

### 6. 可选 yt-dlp 后备引擎

如果未来目标是覆盖更多公开视频平台，可以将 yt-dlp 作为可选后备引擎：

- 自研模块继续处理普通 MP4/HLS；
- yt-dlp 处理公开平台页面；
- UI 上明确标注“使用外部引擎”；
- 错误信息统一回收到当前队列结果机制。

注意：需要处理依赖安装、版本更新、输出路径、进度回调和合规边界。

### 7. 断点续传与失败恢复

当前任务失败后可以重试整个任务，但还没有精细复用已下载切片。后续可做：

- 记录切片 manifest；
- 跳过已存在且大小有效的切片；
- 单切片失败独立重试；
- 合并前校验缺片比例；
- 支持用户手动“继续未完成任务”。

### 8. 更清晰的错误分类

当前错误已经能传播到队列弹窗，但仍可进一步结构化：

- `NETWORK_TIMEOUT`；
- `HTTP_FORBIDDEN`；
- `NO_MEDIA_FOUND`；
- `UNSUPPORTED_DASH`；
- `UNSUPPORTED_DRM`；
- `M3U8_PARSE_FAILED`；
- `SEGMENT_FAILURE_RATE_EXCEEDED`；
- `FFMPEG_FAILED`。

这会让重试策略、用户提示和未来日志导出更可靠。

## 建议迭代顺序

1. 诊断模式 + 会话继承。
2. HLS 多 Key / IV / BYTERANGE 补强。
3. 错误分类与结构化下载报告。
4. 断点续传与切片级恢复。
5. 抽离适配器接口。
6. DASH / MPD 独立适配器。
7. 按实际失败样本添加站点适配器或 yt-dlp 后备。

## 设计原则

- 优先做通用能力，避免每个网站写一次硬编码补丁。
- 不能下载时要解释原因，而不是只显示“失败”。
- 用户已有合法访问权限的网页，尽量继承浏览器会话；但不做 DRM 绕过。
- UI 保持轻量，不把下载页改成复杂专业工具面板。
- 每次扩展都要有自动化测试，尤其是失败原因和边界行为。
